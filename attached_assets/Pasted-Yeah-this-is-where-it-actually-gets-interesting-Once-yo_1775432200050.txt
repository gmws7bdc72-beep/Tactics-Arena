Yeah—this is where it actually gets interesting. Once you accept it’s simultaneous + time-sliced, the game stops being “turn-based soccer” and becomes a deterministic multi-agent simulation with queued intentions.



I’m going to break this down like you’re literally building the engine.

1. TRUE CORE MODEL (what the game 
actually is
)


A fixed-time simulation where each unit executes a precommitted instruction graph, and all interactions emerge from continuous collision + priority resolution.


So instead of:

“Player passes → result happens”



You have:

“Player attempts to pass at time t, while 9 other agents are moving and possibly interfering”

2. TIME STRUCTURE (the backbone)


Each turn = N simulation ticks



Example:

TURN_DURATION = 3.0 seconds
DELTA = 0.05 seconds
TICKS = 60
Main loop:

for tick in 1..TICKS:
    update_player_movement()
    update_ball_physics()
    detect_events()
    resolve_conflicts()
Important insight:

Nothing is instantaneous. EVERYTHING is time-dependent.

3. PLAYER = STATE MACHINE + COMMAND BUFFER


Each player is not just a unit—they’re:

Player:
    position
    velocity
    current_state
    command_queue
    intent_flags
3A. States
enum State:
    IDLE
    MOVING
    DRIBBLING
    PASSING
    SHOOTING
    CONTESTING
    RECOVERING
State transitions are triggered by:

Time (animation completion)

Proximity (collision)

Ball events

3B. Command Buffer (THIS is the “turn-based” part)


Each turn you assign:

Command:
    type (MOVE, PASS, SHOOT)
    target_position
    target_entity
    trigger_time (optional)
Example:

[ 
  MOVE to (10,20),
  PASS to Player_9 at t=1.2s
]
So commands are not just what, but when.

4. MOVEMENT SYSTEM (non-trivial)


Movement is continuous vector motion, not tile snapping.

desired_direction = normalize(target - position)
velocity = desired_direction * speed
position += velocity * delta
BUT add:


A. Acceleration / deceleration
velocity += acceleration * delta
B. Turning cost
Players can’t instantly rotate

Direction changes take time



C. Path smoothing
Avoid jittery zig-zag movement

5. BALL = INDEPENDENT PHYSICS OBJECT
Ball:
    position
    velocity
    owner (nullable)
5A. Dribbling


Ball is “attached” but still slightly lagging:

ball.position = player.position + offset
Offset changes based on:

Movement direction

Speed

5B. Passing


At pass trigger:

ball.owner = null
ball.velocity = normalize(target - position) * pass_speed
Then:

ball.position += ball.velocity * delta
ball.velocity *= friction
6. EVENT DETECTION SYSTEM (THIS RUNS EVERY TICK)


You’re constantly checking:



A. Ball proximity
if distance(player, ball) < control_radius:
    register_control_attempt(player)
B. Player collisions
if distance(playerA, playerB) < contest_radius:
    register_contest(playerA, playerB)
C. Ball path interception (CRITICAL)


Instead of checking line once—you check continuously:

for each player:
    if distance(player.position, ball.position) < interception_radius:
        attempt_interception(player)
This is why timing matters.

7. PRIORITY / CONFLICT RESOLUTION


When multiple things happen at once:



7A. Ball Control Priority


If 2+ players reach ball:

score = f(
    distance_to_ball,
    velocity_toward_ball,
    angle_of_approach,
    reaction_delay
)
winner = max(score)
Optional RNG:

score += random_noise
7B. Contest Resolution


When players collide:

duel_score_A = stats_A + positioning_bonus
duel_score_B = stats_B + positioning_bonus
Result:

A wins → keeps/gets ball

B wins → steals

Tie → ball becomes loose

7C. Action Cancellation


If something interrupts:



Example:

Player begins pass

Gets tackled mid-animation

if interrupted:
    cancel_action()
    ball becomes loose
8. ACTION EXECUTION PIPELINE


Each action is NOT instant—it has phases.

Example: PASS
State: PASSING

Phase 1: wind-up (0.3s)
Phase 2: release (ball velocity set)
Phase 3: recovery (0.5s, player vulnerable)
During wind-up:

Can be tackled → pass canceled

Example: SHOOT
probability = f(
    distance,
    angle,
    defender_proximity,
    pressure_level
)
But shot still exists physically:

Ball travels

Can be blocked mid-flight

9. SPACE CONTROL SYSTEM (this is what makes it “tactical”)


Each player implicitly creates:



A. Influence Radius


Affects:

Pass difficulty

Shot difficulty

Movement safety

B. Dynamic Pressure Map


You can literally model:

pressure(x,y) = sum over defenders:
    weight / distance_to_defender
Then:

Higher pressure → worse outcomes

10. PREDICTION VS COMMITMENT


This is the core gameplay mechanic:

You predict opponent movement

You commit actions without reacting



So design must ensure:



A. No mid-turn input
Otherwise skill becomes reaction-based



B. Outcomes are readable
Player understands why something failed

11. EDGE CASE SYSTEMS (you NEED these)


A. Loose Ball Logic
if no owner:
    nearest player auto-attempts control
B. Simultaneous Interactions


Example:

Pass + tackle + interception at same tick



Solution:

Process in order:

Movement update

Ball update

Collision detection

Resolve conflicts

C. Determinism (important for fairness)


Given same inputs:

Simulation must produce same result



So:

Seed RNG per turn

Avoid floating-point chaos (or control it)

12. WHAT ACTUALLY MAKES IT FEEL LIKE FTA


Not graphics. Not soccer rules.



It’s these:



1. Time-based commitment
You’re planning future states



2. Spatial prediction
“He’ll be there in 1.2 seconds”



3. Emergent chaos from simple rules
No scripting, just systems colliding

13. If You Wanted to Build It (Minimum Viable Engine)


You NEED:

Tick-based simulation loop

Player state machines

Command queue per player

Continuous movement system

Ball physics object

Collision + proximity detection

Priority resolver

Action phase system



Everything else is polish.
